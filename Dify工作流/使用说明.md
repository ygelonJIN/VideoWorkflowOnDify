# Dify HTML 视频工作流使用说明

两个 Workflow 的最后一步使用同一条命令：

```bash
bash '/Volumes/TUF ESD-T1A Media/视频工作流/HTML视频项目/workflow_runtime/tools/run_dify_output.sh' 你的项目名
```

命令会自动打开 TextEdit。把 Dify 完整输出粘贴到 TextEdit，不要粘贴到终端。内容完整后自动继续，不需要回车、`END` 或读取剪贴板。

除了原始 JSON 输出，也支持完整的“视频内容生产资料”报告格式：只要内容同时包含 HTML 和批准包中的 `approved_script.voiceover_script`，脚本会提取口播并进入黑帧渲染，不再只生成 HTML 预览。

## TXT 保存位置

TextEdit 输入文件保存在：

```text
/Volumes/TUF ESD-T1A Media/视频工作流/HTML视频项目/Dify输出/项目名-年月日-时分秒-dify-output.txt
```

例如本次 `333` 的文件是：

```text
/Volumes/TUF ESD-T1A Media/视频工作流/HTML视频项目/Dify输出/333-20261023-165412-dify-output.txt
```

每次运行时，终端也会打印本次 `.txt` 的准确路径。

## 自动分流

| Dify 输出 | 自动处理 | 结果 |
|---|---|---|
| `html_document` | 检查 HTML、移除墙钟驱动、校准技术时间轴 | HTML 预览 |
| `html_document` + `voiceover_script` | TTS、同步字幕、渲染 | 零数字人/零黑帧占位的无数字人 MP4 |
| `html_document` + `heygen_response_json` | 下载媒体、同步字幕、渲染 | 带数字人最终 MP4 |

项目名建议使用唯一的 `请求编号`，不能包含 `/` 或 `\`。

## 黑帧口播视频（04，当前默认）

导入：

```text
Dify工作流/04_黑帧口播_分组生成.yml
```

该 Workflow 不调用 HeyGen API，输出 `html_document`、`voiceover_script`、`approved_package_json`，以及 `motion_report_json`、`merge_warnings_json` 两份动效诊断。它在 Dify 内只生成文案和 HTML，不生成音频；音频由本地统一入口生成。

`02_黑帧口播无数字人视频工作流.yml` 和 `03_仅生成HTML预览工作流.yml` 已停用，挪到 `Dify工作流/归档/`，只作历史备份；02 的能力由 04 接管。

执行边界：

```text
Dify（mimo-v2.6-pro）生成 HTML + voiceover_script
→ 本地 run_dify_output.sh
→ 本地 MiMo TTS（mimo-v2.5-tts）生成 媒体/口播.mp3
→ 本地按完整句子和真实转写时间码生成 字幕/
→ 本地 HyperFrames/FFmpeg 渲染 成片/最终视频.mp4
→ `normalize_final_audio.py` 标准化响度，`check_final_video.py` 校验最终媒体主时钟
```

字幕文字以 `voiceover_script` 为唯一真值，ASR/时间码只负责对齐；每个完整句子单独一条，不截断、不拼接半句。最终画面必须零占位：没有数字人、avatar 媒体层、黑帧小窗、纯黑保留区或等价空白窗口；具体构图由模型自由设计。

渲染失败时不会再只给一段 traceback：

- `render.sh` 在每一关开始前记录阶段名，失败时打印 `❌ 失败关卡：检查真实 DOM 排版（check_html_layout.mjs）（退出码 1）`；
- `build_black_frame_project.py` 会边渲染边保存完整日志，失败时把**阶段名、时间、项目路径和最后 40 行日志**写进项目根目录的 `失败原因.txt`；
- 半成品移动到 `失败项目/项目名-时间戳/`，`失败原因.txt` 跟着一起移动，打开就能看到是哪一关挂的、报了什么。
- 渲染后会自动跑 `detect_blank_frames.py`：检测成片里孤立的空帧（黑闪）；命中时 `repair_blank_frames.py` 用前一帧替换并复查，不再人工发现。


黑帧 Workflow 的 Dify 开始节点提供 TTS 可视化配置，不用在命令里写参数：

| 配置项 | 可选项/默认值 |
|---|---|
| TTS 供应商 | `mimo`（默认）、`macos`、`openai-compatible` |
| TTS 模型名 | `mimo-v2.5-tts`（留空也使用该值） |
| TTS Base 地址 | `默认（按量付费）`、`Token Plan - 中国`、`Token Plan - 新加坡`、`Token Plan - 欧洲` |
| TTS 声音 | `mimo_default`（默认）、`冰糖`、`茉莉`、`苏打`、`白桦`、`Mia`、`Chloe`、`Milo`、`Dean` |

默认声音是 `mimo_default`。本地 MiMo TTS 使用 `MIMO_API_KEY`，默认模型 `mimo-v2.5-tts`；Dify 选择的配置会写入 `approved_package_json.tts_config`，本地自动读取。

输出：

```text
/Volumes/TUF ESD-T1A Media/视频工作流/HTML视频项目/项目名/成片/最终视频.mp4
```

## Dify 配置

只有全合一 Workflow 需要 HeyGen 配置；仅 HTML 和黑帧口播 Workflow 不读取或使用 HeyGen API Key：

| 变量 | 说明 |
|---|---|
| `HEYGEN_API_KEY` | HeyGen API Key |
| `HEYGEN_API_BASE` | 默认 `https://api.heygen.com` |
| `HEYGEN_AVATAR_ID` | 数字人 ID |
| `HEYGEN_VOICE_ID` | 中文声音 ID |

Dify 的 Xiaomi MiMo 官方插件只提供 LLM，插件 manifest 明确为 `llm: true`、`tts: false`。因此：

- Dify 的 MiMo 插件使用 `mimo-v2.6-pro` 生成口播文案、HTML 和结构化数据。
- Dify 不生成音频，也不保存 `MIMO_API_KEY` 供本地 TTS 使用。
- 本地 `build_black_frame_project.py` 读取 `MIMO_API_KEY` 和 Dify 的 `tts_config`，通过小米 MiMo 平台的 OpenAI-compatible Chat Completions 音频接口调用 TTS。
- TTS 返回的 MP3 写入项目的 `媒体/口播.mp3`；本地转写只用于生成时间码，字幕文字仍以 Dify 的 `voiceover_script` 为准。
- 如果 MiMo TTS 返回 401，请检查本地 `MIMO_API_KEY` 是否为有效 Xiaomi MiMo API Key，以及 Key 类型是否匹配所选 Base 地址；不要把 Key 写入项目文件或日志。
- 如果以后要让 Dify 直接产生音频，也可以不用官方 TTS 插件，自己加 Dify HTTP Request 节点或自定义插件，在节点里配置模型名、Base 地址、声音和鉴权；但完整 MP4 的字幕、HTML 动画和 HyperFrames/FFmpeg 渲染仍需要本地完成。

## 提示词链路与质量门禁

当前提示词不是只负责“写一段文案”，而是按生产链路分工：

| 节点 | 职责 |
|---|---|
| A01 任意主题需求整理 | 把任意形态输入（聊天记录、会议纪要、文章、语音转写、清单、想法）整理成 Brief，并产出 `distill`：一个主张 + 支撑它的论点 + 证据 |
| A04 内容策略 | 只选一个有事实支撑的核心角度，把 `distill.arguments` 排成 `argument_order`，排除不讲的内容 |
| A06 口播文案 | 第一句 = 主张，随后按 `argument_order` 展开论点，输出完整口播、逐句字幕真值和 `argument_coverage` |
| A08 分镜导演 | 按口播句子自由划分镜头，每个场景标记 `argument_id`，按论点顺序排列，明确内容重点、visual_brief 和语义过场 |
| A10 动效导演 | 把分镜变成绑定句子的目标级动作、状态变化和过场 |
| A12 事实与合规 | 检查数字、案例、承诺、示例标记和发音风险 |
| H00 拆分场景组（仅 04） | 把分镜切成四组，并给每组带上 `thesis`、本组 `arguments` 和前后衔接钩子 |
| H01S 生成 HTML 骨架（仅 04） | 只输出设计系统、`.scene` 居中布局、四个场景占位和主时间线脚本 |
| H02A–D 场景组（仅 04） | 每组只写自己的场景 markup、`.gX-` 样式和 `data-anim` 动效脚本，立即 `__sceneBuilders.push` |
| H03 合并场景组（仅 04） | 替换占位、包装裸脚本（不碰主时间线）、输出 `motion_report_json`（每组动作数、未命中选择器、`coverage` 组件动效覆盖率、未动组件）与 `merge_warnings_json` |
| H01 HTML 视频编排 | 读取 `approved_package_json`，先做设计定调，再从本屏证据推导组件形态，最后落地 HTML、排版和 GSAP 时间线；不写字幕，字幕由本地注入 |
| H01b 净化 HTML 输出 | 去掉 Markdown 围栏、剥离误吐出的 `<tool_call>` 块，从 `<!doctype html>` 截到 `</html>`；提取不到 HTML 时保留原文，交给 H02 报错定位 |
| H02 HTML 检查 | 只拦 7 项渲染致命项：缺 `#stage`、缺字幕占位、没有 `window.__timelines`、没有 GSAP 动作、用了 `rAF`/`performance.now`、残留工具调用文本、缺 HTML 文档头；其余（画布 CSS、字幕样式、scene 锚点、媒体占位、渲染模式标记）全部只写 warning，本地渲染前会补齐 |

## 字幕与动效的职责边界

- **字幕不交给模型**：H01/H01S/场景组的提示词里已经不要求字幕容器、字幕条目和字幕样式；`sync_video.py` 在渲染前注入容器并按真实时间码逐句上屏，缺容器会自动补。想完全自己写，把 SRT 放到 `字幕/手写字幕.srt`（或 `字幕/最终字幕.srt`），渲染时优先使用它并跳过自动切句。
- **动效交给模型拉满**：提示词要求画面里每个组件都要有自己的动作（进入 + 至少一次状态变化），只做整屏淡入算没做。`H03` 的 `motion_report_json` 会给出每组的 `coverage` 和 `uncovered`，用来判断哪个组件被漏掉了。
- **04 的收尾输出里有诊断**：`motion_report_json`（每组动作数、未命中选择器、组件覆盖率）和 `merge_warnings_json` 现在直接出现在 End 节点的输出里，跑完在 Dify 输出文本里就能看到，不用点进节点详情。
  - `unmatched` 非空 = 选择器找不到元素，先修选择器，不要先调提示词；
  - `coverage` 低于 1 看 `uncovered`，那是从头到尾没动过的组件。

## 输入提炼层（A01 → A03 → 下游全员）

`A01` 不再只是"整理主题"，它对任何输入形态都先做一次提炼，结果写进 `brief.distill`：

| 字段 | 说明 |
|---|---|
| `source_form` | `chat_log` / `meeting_notes` / `article` / `voice_transcript` / `list` / `note` / `idea` / `brief` / `mixed` |
| `thesis` | 一句话主张，必须是判断句，不是话题名词 |
| `thesis_source` | `user_stated` / `implied` / `inferred_from_facts` |
| `arguments[]` | 支撑主张的论点，条数由素材决定；每条含 `id`/`claim`/`evidence`/`support`/`strength` |
| `counterpoints` | 素材里需要正面回应的相反说法 |
| `dropped` | 被丢弃的类别（寒暄、重复、跑题、时间细节） |
| `open_questions` | 素材没讲清、成稿不得编造的点 |

`A03` 会据此给出 `argument_count` 和编排参考时长（`target_duration_seconds` 只是 HTML 编排参考，最终以真实口播为准），并把 `source_text_is_material_only`、`no_chronology_retelling`、`argument_spine`、`no_length_quota` 写进 `brief.hard_rules`。**不设字数、句数、论点数、页数配额**：素材长度不决定视频长度。

`A07` 只拦三件事：JSON 无法解析、口播里没有完整句子、**时间连接词成串（≥5 处，说明在按过程复述）**。除此之外不设任何字数、句数、论点数配额，其余内容判断全部写进 `copy_warnings_json` 和 `script_json.content_diagnostics`，**不阻塞、不触发强制改写**，由你人工判断要不要重跑：

| 诊断项 | 看什么 |
|---|---|
| `chronology_words` | 时间连接词出现次数，成串说明在复述过程 |
| `verbatim_ratio` | 与原始素材 8 字片段的重合率，偏高说明在照抄 |
| `dialogue_marks` | "他说/我说"这类转述处数 |
| `covered_argument_ids` | 模型自报讲到了哪些论点，和 `argument_ids` 对比 |

H01 现在会读取 `approved_package_json`，不再凭空生成通用 HTML；A01 至 A12 也都会读取各自上游变量。每次运行可以通过 `request_id` 选择一个作者期变体，制造布局、组件、动效和过场差异，但运行时禁止 `Math.random`、随机时间和随机颜色。

H01 在 02/03 工作流使用 `temperature: 0.4`，01 工作流仍为 `0.6`。02（黑帧口播）一旦 HTML 没生成成功，本地入口会把整份输出判成“不完整”并空转到超时，所以这条链路优先保成功率；01 有数字人链路没有这个死等机制，继续用高温度换布局差异。02/03 的提示词开头新增「输出协议（最高优先级，违反即失败）」：回复必须以 `<!doctype html>` 开头、`</html>` 结尾，禁止任何工具调用和 HTML 之外的输出，`generated_image` 场景改用 CSS/SVG 表现。02 的 A16 还会把 `visual_source` 为 `generated_image` 的分镜确定性归一成 `reusable_ui_template`（黑帧链路本来就没有出图能力），并把归一结果写进 `storyboard.validation.warnings`。如果 H01 仍然吐出工具调用，H02 的第一条错误会是“输出中残留工具调用文本，必须只输出 HTML”。H01 的设计部分只约束“统一性与语义”（一个视觉隐喻贯穿全片、同一套组件语法、动作必须对应口播里的词或状态变化），**不给组件清单和风格清单，也不设页数、每屏句子数、组件数量、字阶档数、间距基准和动效条数**：密度和形态都由这一屏要给出的证据决定，允许排满也允许留白。技术侧仍强制：根画布、scene 与字幕锚点、媒体占位、统一时间轴、无运行时随机。

本地 `check_html_contract.py` 也只拦致命项（缺根画布、缺字幕占位等），其余检查打印警告后继续渲染；`check_html_layout.mjs` 和 `check_motion_profile.py` 一律只报告。**成片优先级高于检查通过率**：宁可交一条有版面瑕疵的视频，也不要因为一条 warning 卡在渲染前。

## 当前仍保留的规则

内容输入已经改成主题优先：

- 可以只输入一句话、一个想法、一段经历或任意原始文本。
- 不预设行业、商业结构或转化目标；输入里没有的字段一律留空，不做任何默认填充。
- 只有用户明确提供时，人物、价格和行动建议才会进入事实字段。
- 随口输入不会被自动补成背景故事、商业故事或转化文案。

仍保留的内容质量规则：

- 一条视频聚焦一个核心角度。
- 分几段、每段多长由论点重量决定；最后一个单元可以是总结、`ending` 或 `summary`，只有用户明确要求时才强制 CTA。
- 标题要短到能一眼读完，屏幕主文案同理；具体字数由模型判断。
- 每个单元有一个明确观点，优先使用用户已确认的细节、数字、步骤、对比或经历。
- 禁止编造事实、空洞口号、鸡汤、套话和时间线流水账。
- 论点优先：全文只有一个结论，第一句就是它；之后每个论点 1–2 句，先论点后证据，顺序按 `argument_order` 而不是素材顺序。
- 原始输入只是素材，不是提纲：成稿必须打乱原话顺序和对话结构，先给结论再给论据；连续 3 句与原顺序一致就要重排。
- 聊天记录按素材处理：先压成一个结论 + 支撑它的理由，再用自己的话写成面向观众的叙述；禁止逐句转写、禁止“他说/我说”式复述，多话题只取一个。
- `distill.dropped` 里的内容不许写回成稿；`open_questions` 里的内容不许编造答案。
- 标题是钩子而不是概括；每个单元要能一句话说清“观众这 5 秒记住什么”；结尾留一句能被单独引用的金句。
- A17 的`result_summary`不再输出固定字段块，改为`内容信息`（主题 / 目标时长 / 核心结论），字段缺失时整段不出现。

仍保留的技术规则：

- 1080×1920、9:16、简体中文。
- 完整句子字幕、真实时间码、GSAP 时间线和媒体占位。
- 无墙钟驱动、无运行时随机。
- HTML 排版、组件、视觉和过场由模型自由设计。

## 自动修订与 JSON 容错

### 口播自动修订

`A06_生成口播文案` 不设字数和句数配额：讲透就停，写多长成片就多长。`A07` 只要求至少有一个完整句子（否则无法生成逐句字幕）。

第一次不通过时，Workflow 会携带 `copy_errors_json` 进入 `A06R_按错误自动改写口播`（提示词要求按错误类型改：删过程句、重写照搬句、补漏讲论点），再由 `A07R_复查自动改写口播` 和 `A07R_口播复查门禁` 复查。仍不通过时输出具体字数、句子数和错误内容。`A07R` 与 `A07` 使用同一份校验代码，避免复查口径和首次校验不一致。

### JSON 降级处理

- 分镜 JSON 无法解析时，根据口播句子生成基础分镜继续。
- 动效 JSON 无法解析时，生成至少 6 条基础语义动效继续。
- 合规 JSON 无法解析时，按 `needs_changes` 返回可诊断结果。
- 口播 JSON 无法解析时，返回可重试错误并自动改写一次。
- Brief JSON 不预设行业、受众或转化字段；缺失时使用通用主题字段继续，并在 `brief.normalization_warnings` 中记录，不把占位内容当成用户确认事实。

降级处理用于避免模型字符串引号、截断或尾逗号直接触发 `json.decoder.JSONDecodeError`，但不能绕过事实、主题和发布前人工复核。

## 技术约束与创作边界

- 画布始终为 `1080×1920`，这是输出规格，不是页面布局模板。
- 主要内容必须落在安全可读区域内；构图可以自由设计。主内容垂直中心落在 700–1100px 为舒适区，640–1160px 为硬边界：偏离舒适区只记警告，超出硬边界才判失败。装饰层（透明度或字色 alpha 低于 0.35、渐变文字）不参与重叠判定，真实文字互压仍然判错。
- 内容少时可以留白，也可以扩展视觉元素，不强制放大或铺满。
- 完整版：必须保留数字人小窗；小窗和状态条的位置与尺寸由模型设计。字幕固定为 `bottom:13%`、宽度随文字自适应（上限 80%）、45px 字号、1.35 行高和白色无底板文字（只有柔和黑色投影）。
- 无数字人版本（历史模式名 `black-frame`）：必须零占位。禁止数字人窗口、头像、人物媒体、黑帧小窗、纯黑保留区和等价空白窗口；删除窗口后必须回收左上/右上区域，顶部内容不得继续向右避让或保留空槽。
- 场景和字幕由 HyperFrames 时间线驱动，禁止墙钟驱动。
- `媒体/口播.mp3` 实际时长是唯一主时钟；场景先从作者期时间等比映射到真实时长，GSAP 相对偏移使用同一比例，transcript/ASR 字幕使用绝对秒。已经校准的真实时间禁止再次乘以 `timelineScale`。
- BGM 自动补齐到真实成片时长，最终 MP4 的视频、音轨和口播时长差必须小于 100ms。
